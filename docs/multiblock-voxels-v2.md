# Voxel V2 — multiblock physics and targeting

**Status:** First opt-in implementation on draft Bronze PR #11; the Bronze Foundry is the reference machine. Existing Stone/Copper machines retain their previous voxel behavior.

## Authoring contract

Voxel V2 separates **static visual meshes**, **physical collision**, **targetable selection outlines**, and **interaction regions**. It does NOT turn every visible bolt into a collision box.

A machine design can author `voxels` alongside named model solids in `tools/multiblock-models/designs/<machine>.json`. `build-designs.mjs` emits a runtime datapack definition at `data/magneticraft2/multiblock_voxels/<machine>.json` containing:

```json
{
  "format": 1,
  "unit": "model_pixels",
  "collision": [[0, 0, 0, 16, 16, 16]],
  "selection": [[0, 0, 0, 16, 16, 16]],
  "zones": {
    "input": [[0, 0, 14, 16, 16, 18]]
  }
}
```

Boxes are `[minX,minY,minZ,maxX,maxY,maxZ]` in 1/16 block units, measured relative to the controller block's lower/northwestern corner. Values can be negative or extend outside the controller. All 3 axes are real model-pixel coordinates; never normalize a large machine into 0–16.

The canonical orientation is **SOUTH**, exactly like the Rendering V2 model exporter. Other directions are generated by rotating X/Z around the controller center (8,8 pixels). Y never rotates. `collision` is mandatory, `selection` defaults to collision when omitted, and `zones` is optional. Zones are tested in authored order and only affect interaction routing, not physics.

A JSON multiblock opts in explicitly via `settings.voxel_profile: "magneticraft2:<machine>"`. Without it, the existing physics remains. Malformed profiles are rejected on datapack reload; an opted-in Foundry refuses formation if its profile is missing rather than silently substituting a large cube.

## Runtime and caching

- Forge's server-side `AddReloadListenerEvent` registers the Voxel V2 loader. Datapack profiles are validated and their four directional `VoxelShape` objects are compiled **once per reload**.
- Formation reads the cached directional shapes. Both the controller and each already-formed filler receive **local** collision and selection snapshots. The full multiblock collision is never reconstructed on entity movement or camera changes.
- Only selected blueprint `settings.render_air_anchors` become non-occluding physical proxy blocks; unconfigured hollow space remains air. Selection is clipped to its cell, so targeting one part cannot steal clicks from distant cells. The tap's short physical nose may protrude up to half a block past its explicitly declared proxy, preserving the existing gameplay fix.
- Each snapshot is saved in NBT and sent to clients through normal block-entity update packets. Thus **server-selected voxel profiles**, including datapack edits, define authoritative collision without assuming a resource pack on the client has the same files.
- The controller now owns local shapes too, instead of an oversized 3×2×3 hitbox. Old formed Foundries without snapshots retain their previous shape until dismantled and reformed.
- A reload of shape definitions does **not** silently mutate already formed machinery. Reform a machine to apply new profile data. No background shape re-evaluation per tick.

## Foundry integration

The Foundry has 22 simplified collision boxes and 26 selection boxes, authored separately from its 99 decorative/render solids. The firebox and crucible remain hollow. The tap valve's top handle, vertical stem, and lower mounting bracket have independently authored selection-only boxes. Players can target the entire assembly without creating thin, snagging physical collision.

The interaction regions are named `firebox`, `crucible` and `tap`. Right-click currently displays the named region as prototype feedback; it does **not** burn fuel, melt metal or transfer liquid yet. These zones will later let us target the heat source, crucible and tapping assembly without a GUI.

The construction recipe and JSON shape remain unchanged: 15 Bricks and a controller, 3×2×3. The two upper required-air cells become V2 proxies only after successful formation.

## Test locally

```bash
node tools/multiblock-models/build-designs.mjs --self-test
node tools/multiblock-models/build-designs.mjs --check
node tools/multiblock-models/generate.mjs --self-test
node tools/multiblock-models/generate.mjs --check
node tools/multiblock-models/test-voxels.mjs
./gradlew compileJava
```

The self-contained voxel test checks source/export parity, four rotations, hollow firebox/crucible, supported tap, selectable valve, 18 static model hosts per direction and a synthetic 9×5×9 (405-cell) case. It is **not** an in-game benchmark of 405 filler block entities.

In Minecraft: rebuild and **re-form the Foundry**, test all four facings and the upper air anchors, approach and leave the firebox/crucible/tap, walk along the tap while changing camera direction, then save/reload and test chunk boundaries and destruction. The three clickable regions should show distinct actionbar messages.

## Limits and future work

This does not yet implement dynamic voxel collision for moving mechanisms or reduce the number of block entities per filler. Very large machines still require benchmarking BE count, NBT snapshot size, collision box count, chunk save costs and unformed restoration across unloaded chunks. The first profile format caps boxes to avoid unbounded resource-pack input.

The Foundry's earlier hand-authored shapes remain as fallback for old worlds until re-formation. Do not mistake generated visual meshes, selection shapes and physical collision for interchangeable things.
